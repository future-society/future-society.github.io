# Agent notes for future-society.github.io

## Site structure
- Single-page site, duplicated per language: `index.html` (EN), `index.de.html`,
  `index.fr.html`. No templating/build step — each is a full standalone copy.
  Any content change requested for "the website" generally needs to be applied
  to all three, with UI chrome (labels, buttons) translated but people's names,
  paper titles, and citations left as-is.
- Section markers use HTML comments (`<!-- FOCUS AREAS -->` etc.) matching the
  `<section id="...">` right below them — grep for the comment to jump fast.
- Data-driven sections (Team, Projects/"Get concrete", Ways to participate) are
  rendered by inline `<script>` at the bottom of each HTML file (or
  `assets/team.js` for Team) from a JS array — edit the array, not generated
  markup.

## Focus Areas publications list
- Each `.focus-card` has its own `<div class="focus-publications">`: a
  `<button class="focus-pub-toggle" onclick="toggleFocusPubs(this)">` plus
  `.focus-pub-body > .focus-pub-inner > ul.focus-pub-list` for just that
  tile's publications (no shared/combined list below the grid — tried and
  replaced). Uses the Participate (`.way-body`) JS-toggle mechanism, not
  `<details>` (animating `<details>` via `::details-content` was jerky in
  Firefox). Button label is one word; the "+"/"×" is CSS (`::after`), not text.
- Every `.focus-card` needs exactly 4 children (num, h3, p,
  `.focus-publications`) — it's a `subgrid` spanning 4 rows so toggles align.
- `.focus-pub-list` items: title wrapped in `<a>` to the DOI/landing page
  (`target="_blank" rel="noopener"`), then `<span class="focus-pub-meta">Venue
  · Year</span>` (short venue, e.g. "ACM FAccT · 2026"; arXiv → "Pre-print ·
  Year"). Authors deliberately omitted. Find the real DOI/URL by searching
  title+authors; if none exists (unpublished working paper), leave plain text,
  no fabricated URL. Titles not translated. No `white-space: nowrap` on the
  `<a>` — long titles must wrap or they overflow on mobile.

## Team section
- Former Members list (`formerMembers` in `assets/team.js`) is one line per
  person, no bio; optional `photo` field renders a round `.former-avatar`.

## Collapsible content
- Default pattern: plain `<details><summary>...</summary>...</details>`, no
  JS, `+`/`–` marker via `summary` CSS (see `.event-archive`, `.team-former`).
  Exception: Focus Areas publications (see above, JS-toggle for a reason).
  Summary label text is translated per language file.

## Non-website / email-task requests
- Not every email instruction maps to a site edit — some (LinkedIn drafts,
  research asks) are pure drafting tasks with no file to change other than
  the deliverable itself.
- No outbound email-sending tool exists; Gmail MCP needs OAuth the user must
  grant interactively, which a non-interactive run can't do. Never claim an
  email was sent — write the deliverable to a file so it becomes the
  OUTPUT_FILE attached to the reply.
- FuSo's LinkedIn company page (linkedin.com/company/future-society-hub/) is
  login-walled, not fetchable — ground drafts in futuresociety.ch/llms.txt
  instead and say so explicitly in the draft.

## Social icons
- Two places use inline-SVG social icons, not `<img>`/icon fonts: nav bar
  (`.nav-social`, LinkedIn only, in every `<nav>`) and Contact section
  (`.contact-social`, a flex row of icon links below the `fuso@unisg.ch`
  mailto, added below the postal address paragraph — LinkedIn + BlueSky so
  far). Both just set `color`/`hover:color:var(--accent)` on the `<a>` and
  rely on `fill="currentColor"` in the `<svg>` — reuse the exact `<path>`
  markup (Simple Icons-style paths) rather than re-fetching/re-drawing when
  adding another platform, and add new platforms to both places if the ask
  is "site-wide", not just one.

## CSS grid
- Sections use a shared `.grid` (grid-column per element), not flex/block.
  New full-width blocks after a `-grid` element typically use
  `grid-column: 3 / -1`, must be added to the tablet-breakpoint reset list
  (`grid-column: 1 / -1` around `.focus-intro, .focus-grid, ...`), plus a
  mobile-stacking rule if it's itself a multi-column grid.

## Nav submenu / audience deep links
- Participate's `<ul class="nav-sub">` links to
  `#participate-students|-researchers|-policy|-industry|-all`; a router in
  each file's inline script watches `hashchange`, calls `filterWays(key)` and
  scrolls to `#participate`. Unknown key → ignored, page behaves normally.
- Submenu rules are scoped to `#navMenu`/`#navMenu > li`, not `nav ul` —
  reverting to `nav ul` makes it inherit `position: absolute; top: 56px` and
  cover the page. Above 1100px items stretch to bar height for hover;
  below 1100px shortcuts render inline, always-visible.

## AI+X deck (`ai+x/index.html`)
- Standalone reveal-style single-file deck (~600KB, mostly inline base64
  SVG/image data), not templated from anything else. Each `<section
  id="sN" ... data-title="..." data-time="M:SS" aria-label="Slide N">` is one
  slide; a bottom `<script>` builds the actual navigable slide list purely
  from DOM order (`[...document.querySelectorAll('.slide')]`), so the real
  source of truth for slide order is section position in the file, not the
  `id`/`aria-label` numbers — but those numbers (plus each slide's own
  in-slide `<span class="pos">NN / 11</span>` and prev/next `href="#sN"`
  arrows in `.topline .num`) are just hardcoded text/attributes that must be
  kept in sync manually when reordering, or the on-slide ‹/› arrows jump to
  the wrong neighbor. Title slide (`s1`) and the keynote-handoff slide
  (last, `s11`, `.topline` uses the `.partners` branding layout) have no
  pos/prev-next chrome at all — only the middle slides do.
  `data-time` is a cosmetic per-slide pacing cue shown in the on-page
  overview panel, cumulative minutes:seconds into the deck's own delivery —
  keep it roughly monotonic across slide order when moving a slide, it isn't
  auto-derived. When reordering, don't hand-edit with Edit/sed given the
  giant base64 lines — extract exact `<section>...</section>` byte ranges
  via `grep -n "<section id=\|^</section>"` and reassemble with a small
  Python script instead.
- The deck's own agenda list (Programme slide, `ol.agenda > li ><span
  class="dur">`) is a separate, independent set of durations from the
  above — it's what the *event* schedule says each segment gets, not how the
  deck paces itself internally. Keep the total (2.5 hours) unchanged when
  reassigning minutes between agenda items unless told otherwise.

- Music-note button in the hero's bottom-right opens an `EN/DE/FR/IT` pill;
  picking one plays that song via a single shared `<audio id="fuseSong">`
  (src swapped per pick, keeps `preload="none"` and the analytics.js src-based

  otherwise. Escape/outside-click close the picker but don't stop playback.
  Picker codes are the SONG's language, not the page's — not translated.
  `I-faccio-FuSo.mp3` (Italian) is reachable only here (no `index.it.html`).
- Positioning is load-bearing: the note hangs off `.hero-logo` (wrapper
  around the logo img), tangent to the logo's inscribed circle at 4:30 via
  `calc(50% + 0.7071 * (50% + 25px))` — keep the formula, it holds at any

  into the clear band below — a pill this wide crosses circuit lines if
  opened from the note itself. Never move the note to the hero's top-right
  (collides with the nav EN/DE/FR switch). Colour is the logo's own accent
  green; hover/playing FILLS the circle rather than recolouring it.

## LinkedIn post draft requests
- Recurring email task: find a world-news story ≤2 days old that matches a
  FuSo focus area, draft a LinkedIn post tagging relevant entities, and tie it
  to a specific FuSo publication (Focus Areas `.focus-pub-list`s + `llms.txt`
  Publications/Key People). Must not repeat a **news story** already covered;
  reusing a **publication** is fine if the news hook/argument differs.
  New drafts go in `/linkedin-suggestions/` (older root-level
  `linkedin-post-draft*.md` files predate that convention, left in place).
  No email-sending tool exists — the draft file is the OUTPUT_FILE.
- Before picking a publication, `grep -l "doi.org\|arxiv\|openreview"
  linkedin-suggestions/*.md linkedin-post-draft*.md` and check each match's
  DOI against the site's focus-pub-lists — this is authoritative; a
  hardcoded list of "publications used so far" in these notes will drift and
  has been removed for that reason. As of Sept 2026, PermitBot (ICAIL 2026)
  is the only fully unused publication — it has no findable URL and repeated
  targeted searches have found no matching news; every other listed
  publication has been used at least once. The Article 40(12) audit paper in
  particular has been reached for often (six times by end of Sept 2026) since
  its "self-reported vs. independently verified" argument fits almost any
  AI-safety-incident story — when another story's news hook fits a
  less-recently-used publication just as well (e.g. a children's-data claim
  matching the privacy-by-design book), prefer that one over defaulting to
  Article 40(12) again, purely for anchor diversity. A stuck publication's eventual
  match has repeatedly come from its *methodology or design philosophy*
  (rigorous evaluation, keeping the human in the decision loop, real
  behavioral data) or a *second stated application* (check Focus Areas "how"
  text and the authors' team bios), not from searching its literal
  subject-matter — worth trying before concluding a publication is
  unmatchable. The Article 40(12) research-API audit paper (Bekavac & Mayer)
  is a reliable fallback: its core argument (self-reported/voluntary
  disclosure vs. what independent outside scrutiny actually finds)
  generalizes far beyond platform-data-access news, so reusing it on a
  distinct incident is fine, not a sign of running out of ideas. FuSo's two
  books (*AI and Law*, Routledge/CRC 2024; *Designing for Privacy and its
  Legal Framework*, Springer 2018, both Tamò-Larrieux) sit only in
  `llms.txt`/the site's JSON-LD `workExample` block, not in any Focus Areas
  list — a valid anchor when nothing else fits; find the landing page via
  WebSearch (no DOI exists) rather than fabricating one. A genuinely fresh,
  well-sourced story is fair game even without a regulatory/legal peg, as
  long as the FuSo tie-in is substantive rather than cosmetic.
- WebSearch is unreliable for date-sensitive claims — verify the actual news
  hook against a primary source (WebFetch the original outlet, not an
  aggregator) before treating it as fresh. Recurring staleness traps, all
  caught by tracing to the earliest dateable primary article rather than the
  freshest-looking search hit: (a) SEO/aggregator blogspam inventing specific
  agency names/dates not found on the regulator's own site; (b) an old story
  resurfacing as a late recap dated inside the window, or under a new
  headline for the same underlying incident (weeks-old surveys/rulings, a
  wire piece re-covering an incident already used days earlier — same **news
  story**, not a fresh one); (c) flatly invented events; (d) a product/
  feature or industry announcement that genuinely launched weeks or months
  earlier but that aggregators keep re-summarizing as if new (has hit an AI
  shopping-assistant launch, a self-regulatory-body story really from ~10
  days earlier, and a payments feature really from months earlier — each
  time the "fresh" coverage was just recirculation). When citing a specific
  bill number or figure from one outlet's summary, cross-check it against an
  independent tracker/source before using it as the anchor fact. When a
  ≤2-day search keeps surfacing nothing but stale recaps or already-used
  stories, document the rejected candidates in the draft and pick the
  freshest genuinely-new, undupe'd story available even if it's ~1 week old
  rather than forcing a stale story through.

## Dark mode
- Defaults to the browser's `prefers-color-scheme` (auto light/dark); an
  explicit toggle click overrides that and is remembered. State lives in
  `data-theme="dark"` on `<html>`, persisted to `localStorage['fuso-theme']`
  only on click (no stored value = "follow the OS") — shared across EN/DE/FR
  since it's one origin. A blocking inline `<script>` at the very top of
  `<head>` (before the stylesheet `<link>`) resolves stored-choice-or-
  `matchMedia` before first paint to avoid a flash; the toggle's own logic
  lives in the same bottom `<script>` block as the other nav IIFEs (right
  before "Mobile nav"), reading the attribute back rather than re-deciding
  it, plus a `matchMedia('(prefers-color-scheme: dark)').addEventListener
  ('change', ...)` that live-updates the theme if the OS preference changes
  while the page is open and there's no explicit stored override. Button
  markup is two inline SVGs (sun+moon) shown/hidden by CSS off
  `[data-theme="dark"]`, styled like `.nav-social` and always visible
  (outside `#navMenu`, not hidden behind the hamburger) — placed after
  `.nav-social`, before `.nav-toggle`. All three language files need the
  button (translated `aria-label`, updated by the toggle JS on click) and
  both scripts kept in sync.
- Nearly the whole stylesheet is re-themed by overriding 5 vars in one
  `:root[data-theme="dark"]` block (`--black/--white/--gray/--mid/--accent`)
  because almost every rule already reads colour through those rather than
  literal hex — extend dark mode for new CSS by using these vars, not raw
  hex, and it re-themes for free. `--accent` is *relightened* for dark (not
  a literal invert) since the original only hits ~3.7:1 on the new dark
  background — text/links need 4.5:1. That relighten breaks the "same green"
  invariant for white-text-on-accent-fill buttons (would drop to ~2.7:1), so
  those few rules (`.song-note` hover/playing, `.learn-more-btn:hover`,
  `.way-filter.is-active`, `.block-item`) use a separate fixed
  `--accent-contrast` (never overridden) + literal `#fff` instead of
  `var(--white)` for their text — check any new "white text on filled accent
  background" pattern against this list rather than reaching for
  `var(--accent)`/`var(--white)`.
- Three more vars (`--text-body`, `--text-quiet`, `--divider`) exist only to
  dark-theme literal hex colours (`#333`/`#444` body copy, `#555`-`#777`
  muted labels, `#ccc`-`#eee` hairline borders) that had been hardcoded
  instead of using a variable — converted in place to these three rather
  than overridden from a separate dark-mode block, because several of those
  selectors (`.way-filter`, `.ev-host .event-link`, `.talk-item .event-link`)
  have `:hover`/`.is-active` siblings of equal CSS specificity; a same-
  specificity override rule added later in the cascade would have
  permanently beaten the hover state instead of losing to it as intended.
  **If a new literal hex colour needs dark theming, edit it in place to a
  var — do not add a new `[data-theme="dark"] .selector {...}` rule** unless
  you've checked the selector has no same-specificity interactive state.
- The circuit-line under section headings (`.section-label`) is a
  background-image (gradient + `circuit-ring-black.svg`), not a var-based
  colour, so it can't be re-themed via the variable overrides — it's
  `filter: invert(1)`'d instead in the dark block at the end of the file.
- Deliberately left alone: the hero/footer logo images
  (`fuso-logo.svg`, `fuso-logo-white-green_thick_lines.svg`) both have an
  opaque white circular fill (by design, so only the green traces show
  against a white page) — on the dark background they render as a visible
  white disc/medallion rather than blending in. No transparent-background
  variant exists in `assets/`; fixing this needs new SVG asset work, out of
  scope for a CSS/JS dark-mode pass. Revisit only if asked.

## Vanity redirect paths (`cocoda/`, `decode/`)
- Short URLs like `futuresociety.ch/cocoda` are a folder with one `index.html`
  that bounces via `<meta http-equiv="refresh">` + `location.replace(...)` +
  a visible fallback link + `<link rel="canonical">` + `noindex` — GitHub
  Pages has no server-side redirects. `cocoda/` → snsf-cocoda.github.io;
  `decode/` → futuresociety.ch/decode.github.io. To add another, copy an
  existing folder and swap the URL/title in all four places; keep out of
  `sitemap.xml`.
